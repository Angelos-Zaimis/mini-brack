# ADR 0002: UUID v7 primary keys

- Status: Accepted
- Date: 2026-11-10
- Ticket: MIN-10

## Context

Product ids appear in public URLs, in Kafka events, and later in other services (order, payment). We need ids that are
unique across services, can't be guessed, and don't slow down inserts.

## Decision

Primary keys are **UUID v7**, stored in Postgres's native `uuid` type and generated by the application (Hibernate 7
`@UuidGenerator(style = VERSION_7)`), not by the database.

## Why

- **UUID over bigint/sequence:** globally unique across services and events, not guessable (`/products/1, 2, 3…`), and
  known before the insert, so events can carry it and Hibernate can batch inserts.
- **v7 over v4:** v4 is random, so every insert lands at a random spot in the primary key index, causing page splits
  and a fragmented index. v7 starts with a timestamp, so inserts go to the end of the index, almost like a sequence,
  and ids sort by creation time.
- **Generated by the app:** Postgres 17 only has v4 built in (`gen_random_uuid()`); `uuidv7()` arrives in Postgres 18.
  All writes go through the service (including the bulk import), so the app can always create the id.

## Consequences

- 16 bytes per id instead of 8, so indexes are larger. Fine at our scale.
- Plain SQL inserts (manual fixes, scripts) must supply an id; there is no database default.
- If we move to Postgres 18, we can add `DEFAULT uuidv7()` as a fallback.
